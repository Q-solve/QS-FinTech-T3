EXECUTIVE SUMMARY
Fraud Busters is a quantum-enhanced mobile-money fraud detection demonstration system purpose-built for the Q-Solve 2026 hackathon. This document defines the complete frontend architecture: technology stack, component design, data contracts, visualization strategy, state management, accessibility requirements, security posture, and demo-resilience engineering.

The frontend is not a generic fintech dashboard. It is a fraud intelligence command center designed to answer five questions a judge can verify in under three seconds:

What problem does Fraud Busters solve?
What transaction is being evaluated?
What score did the model return, and which model produced it?
How does QSVM compare with classical baselines?
What is real, what is simulated, and what remains a prototype limitation?
Every architectural decision in this document serves those five questions, the 12-minute live demonstration window, and the responsible quantum-computing narrative that defines the project's integrity.

1.2 Technology Stack Recommendations with Justifications
Layer	Technology	Version	Justification
UI Framework	React	19.x	Component model maps directly to modular fraud dashboard cards; concurrent features handle async ML responses gracefully; ecosystem depth supports hackathon velocity
Language	TypeScript	5.x	Catches contract mismatches between API response and UI at compile time; critical for schema-driven form generation from dynamic feature configs
Styling	Tailwind CSS	4.x	Utility-first approach enables rapid iteration within hackathon timeline; CSS variable integration supports semantic dark-theme tokens; responsive breakpoints are first-class
Component Library	shadcn/ui	Latest	Pre-built accessible primitives (Dialog, Sheet, Table, Tooltip) eliminate boilerplate; components own their source, enabling hackathon customization without dependency conflict
Routing	Wouter	3.x	Lightweight (< 2KB) client-side router with hook-based API; sufficient for the six-route information architecture; avoids React Router overhead for a demonstration app
Charts	Recharts	2.x	Composable, declarative API on top of D3; accessible SVG output; ResponsiveContainer handles projected-screen resizing; CustomTooltip supports metric definitions inline
Icons	Lucide React	Latest	Consistent icon system with tree-shaking; shield, activity, alert-triangle, and cpu icons directly map to fraud-intelligence narrative
HTTP Client	Fetch API + custom wrapper	Native	No additional bundle weight; interceptors and timeout logic implemented in apiClient.ts abstraction layer
State (server)	TanStack Query (React Query)	5.x	Stale-while-revalidate semantics prevent duplicate analysis submissions; cache keys keyed to request parameters; onSuccess/onError handlers centralize error normalization
State (client)	React Context + useReducer	Built-in	Demo mode, theme, and session state fit Context without Redux overhead; avoids over-engineering for a hackathon scope
Forms	React Hook Form + Zod	Latest	Schema-driven validation matches the dynamic feature configuration contract; Zod schemas shared between form validation and API response parsing
Build Tool	Vite	5.x	Sub-second HMR critical during hackathon iteration; optimized production bundles; TypeScript path aliases supported natively
Testing	Vitest + Testing Library + Playwright	Latest	Unit and component tests via Vitest (same config as Vite); E2E rehearsal flows via Playwright; mock service worker (MSW) intercepts API calls in test and mock modes
1.3 Integration Points with Quantum Backend Services
The frontend communicates exclusively through the Backend API layer. It has no direct connection to qBraid, IBM Quantum, Azure Quantum, or any quantum runtime. All quantum provenance information — qubit count, shot count, simulator vs. QPU, execution backend — is received as structured metadata in the API response and rendered as-received.

Integration shape (API contract):

// POST /api/v1/analyze
interface AnalyzeRequest {
  transaction: Record;
  // Only the 4–8 features agreed by Data/ML and Backend
  // Never includes PII, account names, or phone numbers
}

interface AnalyzeResponse {
  fraud_score: number;                    // [0, 1] inclusive
  model_used: string;                     // "qsvm" | "rbf_svm" | "xgboost" | etc.
  execution_mode?: "live" | "mock" | "cached" | "fallback";
  risk_band?: "low" | "review" | "high"; // Optional; frontend derives if absent
  transaction?: Record; // Echo of submitted features
  metadata?: {
    dataset?: string;
    feature_count?: number;
    qubit_count?: number;
    execution_backend?: string;           // e.g. "qbraid simulator"
    shot_count?: number;
    split_id?: string;
    benchmark_timestamp?: string;
    [key: string]: string | number | boolean | null | undefined;
  };
  benchmark_table?: BenchmarkRow[];
  request_id?: string;
  timestamp?: string;
}

interface BenchmarkRow {
  model: string;
  roc_auc?: number | null;
  precision?: number | null;
  recall?: number | null;
  f1?: number | null;
  status?: "available" | "unavailable" | "error";
}

// GET /api/v1/benchmarks — returns pre-computed benchmark data
interface BenchmarkResponse {
  benchmark_table: BenchmarkRow[];
  metadata?: AnalyzeResponse["metadata"];
  cached_at?: string;
}

// GET /api/v1/health — system status probe
interface HealthResponse {
  status: "ok" | "degraded" | "unavailable";
  model_ready: boolean;
  execution_mode: string;
  timestamp: string;
}
1.4 Data Flow Patterns
ANALYSIS FLOW:
User Input → Form Validation (Zod) → apiClient.analyze() →
  [Mock mode]  → mockFixtures.getAnalyzeResponse() → Result State
  [Live mode]  → POST /api/v1/analyze (with timeout/cancel) →
    [Success]  → Response validation (Zod) → TanStack Query cache → Result State → UI render
    [Error]    → Error normalization → ErrorState component → Retry action
    [Timeout]  → TimeoutError → User-visible retry with request ID preserved

BENCHMARK FLOW:
/benchmarks mount → useBenchmarkResults() hook →
  [Cached in session] → Render from cache immediately
  [Not cached]        → GET /api/v1/benchmarks →
    [Success]         → Cache in TanStack Query → chartTransforms.toBenchmarkChartData() → Recharts render
    [Unavailable]     → Render cached snapshot fixture with "Cached benchmark" amber badge

DEMO MODE FLOW:
DemoContext.activateScenario(scenarioId) →
  SampleScenarioPicker selects fixture →
  TransactionForm pre-fills with fixture values →
  User submits (or auto-triggers in rehearsal mode) →
  mockFixtures.getScenarioResponse(scenarioId) →
  Identical result render path as live mode →
  "Mock demo response" amber badge displayed

2.1 Target User Personas
Persona 1 — Fraud Analyst (Amina, 31, Nairobi)

Daily user of mobile-money monitoring tools
Needs fast triage: is this transaction worth escalating?
Comfortable with financial data but not with quantum computing terminology
Primary interaction: /analyze — load a transaction, read the score, decide next action
Pain points: information overload, slow response times, unclear confidence levels
Design requirement: score readability at a glance; plain-language risk labels; action-oriented UI
Persona 2 — Technical Judge / Quantum Evaluator (Dr. Kioni, 45, CERN/OQI)

Evaluates whether the quantum contribution is genuine and properly scoped
Needs to verify: correct baseline comparison, honest simulator/QPU disclosure, no fabricated advantage claims
Primary interaction: /benchmarks and /methodology
Pain points: vague quantum claims, missing provenance, cherry-picked metrics
Design requirement: complete benchmark table; provenance metadata panel; explicit limitation callout
Persona 3 — General Judge / Financial Stakeholder (Robert, 52, Kenyan banking sector)

Understands mobile-money fraud problem domain but not quantum computing
Needs to see: real-world relevance, practical value, responsible AI framing
Primary interaction: / overview and the live demo on /analyze
Pain points: overly technical explanations, unclear social impact
Design requirement: East Africa context statement; plain-language pipeline explanation; impact framing without fabricated statistics
Persona 4 — Demo Presenter (Team Member, hackathon stage)

Needs reliable, repeatable 12-minute demonstration flow
Primary interaction: /demo rehearsal mode + /analyze live
Pain points: dead states under network pressure, confusing fallback behavior, projector legibility
Design requirement: prepared scenarios; explicit mode badges; projector-safe typography

2.4 Visualization Strategy for Quantum Model Outputs
Risk Score Visualization Principles:

Primary score display: large monospace numeral (display-size, projector-readable) with percentage equivalent
Gauge/meter: segmented horizontal bar (3 segments: Low 0–0.4, Review 0.4–0.7, High 0.7–1.0) with needle indicator
Color + icon + text always presented together — never color alone
Accessible: aria-valuenow, aria-valuemin, aria-valuemax, role="meter" on gauge element
Screen reader: "Fraud score 83 percent. Risk band: Review recommended. Model used: QSVM."
Benchmark Visualization Principles:

QSVM always first in model ordering (visual prominence without distortion)
Y-axis always starts at 0.0 — no truncation to magnify small differences
Metric selector (ROC-AUC / Precision / Recall / F1) allows judges to verify all dimensions
Missing values shown as hatched/empty bars with "Not returned" label — never as zero
Adjacent accessible table with exact numeric values
Quantum Pipeline Visualization:

Five-step circuit-diagram metaphor: nodes connected by lines, each node expandable
Animated signal pulse along connector lines during analyzing state (respects prefers-reduced-motion)
Static fallback: numbered step cards with expand-for-detail pattern

SECTION 4 — TECHNICAL SPECIFICATIONS
4.1 Frontend Framework Selection
React 19 with TypeScript is selected for the following reasons specific to this project:

Concurrent rendering — React 19's concurrent features handle the asynchronous nature of quantum kernel evaluation (potentially slow backend responses) gracefully; useTransition keeps the UI responsive while awaiting results
Component composition — The fraud dashboard decomposes naturally into independent cards (score, benchmark, provenance) that React's model represents well
TypeScript integration — Schema-driven form generation from TransactionFieldDefinition[] arrays and Zod-validated API responses require strong typing to prevent runtime contract mismatches
Ecosystem — shadcn/ui, Recharts, TanStack Query, and Wouter are all React-native, avoiding cross-framework integration overhead
Hackathon velocity — React's developer experience and the existing static template accelerate implementation within the 3-day constraint
4.2 State Management Approach
Rationale for layered state architecture:

// LAYER 1: Server state — TanStack Query
// Handles: API calls, caching, loading/error states, deduplication
const { data: benchmarks, isLoading, error } = useBenchmarkResults();
const analysisMutation = useAnalyzeTransaction();

// LAYER 2: UI session state — React Context + useReducer
// Handles: demo mode, active scenario, latest score (session only, not persisted)
const { mode, activeScenario, latestScore } = useDemoMode();

// lib/apiClient.ts — abstraction layer
interface ApiClient {
  analyze(request: AnalyzeRequest): Promise;
  getBenchmarks(): Promise;
  getHealth(): Promise;

// Live implementation
const liveClient: ApiClient = {
  analyze: async (request) => {
    const controller = new AbortController();
    const timeoutId = setTimeout(() => controller.abort(), ANALYZE_TIMEOUT_MS);
    
    try {
      const response = await fetch(`${API_BASE_URL}/api/v1/analyze`, {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify(request),
        signal: controller.signal,
      });
      
      if (!response.ok) {
        throw new ApiError(response.status, await response.text());
      }
      
      const raw = await response.json();
      return AnalyzeResponseSchema.parse(raw); // Zod validation at boundary
    } finally {
      clearTimeout(timeoutId);
    }
  },
  // ... getBenchmarks, getHealth
};

"How to read this" collapsible:
- ROC-AUC: probability that the model ranks a fraud case above a legitimate one
- Precision: of all transactions flagged as fraud, what fraction actually were?
- Recall: of all actual fraud cases, what fraction did the model catch?
- F1: harmonic mean of precision and recall — key for imbalanced datasets
- Note: "With ~0.13% fraud prevalence in PaySim1, accuracy alone is misleading.
  A model that flags nothing achieves 99.87% accuracy."

SECTION 10 — INNOVATION AND COMPETITIVE EDGE
10.1 Unique Features Showcasing Quantum Computing
1. Quantum Kernel Visualization (Methodology Screen)

A visual representation of how a ZZFeatureMap encodes two transaction vectors into quantum state space, and how the inner product of those states forms the kernel value. Implemented as an SVG diagram with:

Two transaction vectors shown as input nodes
Circuit gate symbols (H, ZZ) on connecting lines
Quantum state representation as unit circle segments
Kernel value output shown as the overlap measurement
Labeled: "Illustrative diagram — shows the encoding concept, not circuit output"
This gives judges a concrete visual anchor for understanding why the quantum kernel differs from a classical RBF kernel, without making unsupported performance claims.

2. Execution Provenance Chain

Every result card shows a traceable provenance chain:

PaySim1 dataset (6.36M rows)
  → 6 selected features
    → ZZFeatureMap (6 qubits, 1 rep)
      → Gram matrix (qBraid simulator, 1024 shots)
        → QSVM classifier
          → fraud_score: 0.83
            → "Review recommended"
This transparency differentiates Fraud Busters from systems that present scores without explainability. Each step is expandable with a one-sentence explanation.

3. Honest Comparison Mode

The benchmark screen includes a unique "honest comparison" design element: a callout card that reads:

> "QSVM is the primary candidate, but we evaluated it against the strongest available classical baselines using identical data splits. The numbers above tell the real story — not a quantum label."

This positions the team as technically rigorous, which is itself a differentiator among hackathon submissions.

4. Execution Mode Transparency System

No other demo system explicitly shows Live / Mock / Cached / Fallback states for every result. The badge system makes Fraud Busters uniquely trustworthy:

[🟢 LIVE · QSVM · Simulator] — "We ran the real model. Here is the result."
[🟡 Mock demo response] — "This is a prepared fixture. Reliable for rehearsal."
[⬜ Cached benchmark · 2026-09-02] — "Benchmark from yesterday's run. Model not connected."
[🟡 Fallback · RBF-SVM] — "Quantum model unavailable. Classical fallback used."
